## 2. Что требуется получить

### 2.1 Каркас решения — Clean Architecture, EF Core + PostgreSQL

- Разложить решение на **отдельные проекты**: `Domain` → `Application` → `Infrastructure` → `Api`.
  Зависимости строго внутрь: `Api → Application → Domain`, `Infrastructure → Application → Domain`.
  Никаких ссылок из `Domain`/`Application` на EF Core, ASP.NET, Redis, RabbitMQ и прочую инфраструктуру.
- **PostgreSQL вместо SQLite.** Провайдер `Npgsql.EntityFrameworkCore.PostgreSQL`, миграции в репозитории,
  автоматическое применение при старте. Подключение — из конфигурации/переменных окружения.
- Миграции должны применяться идемпотентно и не ломаться при повторном старте.
- Git-ветки под каждую крупную работу, слияние в `main` через `--no-ff` (ТЗ требует историю ветвлений для анализа).

### 2.2 API комментариев

- Создание комментария и ответа, каскад **любой** вложенности.
- Сортировка корневых комментариев по **User Name**, **E-mail**, **дате** — в обе стороны.
- Пагинация по **25** на страницу. Сортировка по умолчанию — **LIFO**.
- Данные клиента сохраняются и доступны: имя, e-mail, **сайт (Home page)**, **IP-адрес**, **User-Agent**.
  IP брать честно: за реверс-прокси — из `X-Forwarded-For` (включить обработку forwarded headers).
- Форма: User Name (латиница+цифры), E-mail (строгая проверка), Home page (URL, необязательное),
  CAPTCHA (картинка, обязательное), Text (только разрешённые теги, обязательное).

- Allow-list тегов и проверка закрытия — уже сделано, сохранить.

### 2.4 CAPTCHA

### 2.6 Фронтенд — **Angular**, полная замена прежнего

- Прежний фронт (ES-модули без сборки) **удаляется**, вместо него полноценное Angular-приложение.
- Требуется: форма добавления (с CAPTCHA), таблица корневых комментариев с сортировкой в обе стороны,
  пагинация 25, каскадное отображение ответов с отступом и левой полосой-цитатой,
  AJAX-предпросмотр сообщения **без перезагрузки страницы**, панель кнопок `[i] [strong] [code] [a]`,
  клиентская валидация (зеркалит серверную), визуальные эффекты (lightbox для картинок, модал для TXT),
  подписка на WebSocket с живым обновлением, CSS по образцу `docs/task/page1-X10.png`.
- Сборка Angular — в Docker, multi-stage (node-сборка → статика внутрь образа API или отдельный nginx-контейнер).
- Никаких `node_modules` в репозитории; запуск «с нуля по README» должен работать.

### 2.7 Тесты

- Unit + интеграционные. Интеграционные — против реальных зависимостей (PostgreSQL, Redis, RabbitMQ)
  через Testcontainers **или** через сервисы compose-стека.
- Существующие 251 тест должны продолжать проходить либо осознанно адаптироваться под PostgreSQL.
- e2e-скрипт и QA-чеклист — расширить под новые требования.

### 2.8 Docker / README / схема БД

- Один `docker compose up --build` поднимает **весь** стек: API, Angular (или статика из API),
  PostgreSQL, Redis, RabbitMQ, Elasticsearch. Плюс профиль для нагрузки с k6.
- Проброс портов management-панелей (RabbitMQ), health-check'и и `depends_on: condition: service_healthy`
  для корректного порядка старта.
- README — команды проверены запуском, отдельный раздел «самопроверка с нуля».
- Файл схемы БД, открываемый в MySQL Workbench ( PostgreSQL-диалект — в отдельном файле).

### 2.9 Уровень **Middle** (из плана заказчика)

| Компонент | Что именно |
|---|---|
| **Redis** | Кэш: дерево/страницы комментариев, счётчики, записи CAPTCHA. Инвалидация по событию. |
| **RabbitMQ** | Очередь и брокер: публикация доменных событий, отдельный консьюмер. Обязательно с DLQ/retry. |
| **События** | Доменные события (`CommentCreated` и др.) публикуются в брокер, а не только внутри процесса. |
| **WebSocket** | Broadcast новых комментариев — уже есть, перевести на публикацию через брокер (чтобы работало при нескольких инстансах API). |
| **GraphQL** | Эндпоинт GraphQL рядом с REST (например HotChocolate): запрос дерева комментариев с сортировкой/пагинацией, создание комментария. |
| **Elasticsearch** | Поиск по тексту комментариев, индексация по событию, отдельный поисковый эндпоинт. |

### 2.10 Уровень **Middle+** (из плана заказчика)

- **Заложить в архитектуру** решение под нагрузку: **1 000 000 сообщений** и **100 000 пользователей за 24 часа**
  (~11.6 сообщений/сек в среднем, с пиками). Это не «написать текст», а реально принять решения в коде:
  индексы БД, отсутствие N+1, пагинация без `OFFSET` на глубоких страницах (keyset), батчинг вставок,
  кэширование горячих страниц, асинхронная запись/обработка через брокер, горизонтальная масштабируемость
  (несколько инстансов API за балансировщиком, состояние — в PostgreSQL/Redis/RabbitMQ, не в памяти процесса).
- **Нагрузочный тест на k6** — реально написанный и реально прогнанный, с отчётом:
  сценарий, профиль нагрузки, результаты (RPS, latency p95/p99, ошибки), узкие места и что бы улучшили.
  Конфигурация запуска — в compose-профиле, например `docker compose --profile load up k6`.
- Ручки/эндпоинты для генерации тестовых данных (seed) в отдельном профиле, чтобы наполнять базу миллионом записей.

### 2.11 Cloud-ready — **без запуска в облаке**

Заказчик работ: готовить к облаку, но **ничего в облако не разворачивать**. Всё крутится локально в Docker.

Значит нужно:
- Все внешние зависимости — **за интерфейсами** в `Application` (порты), реализации — в `Infrastructure` (адаптеры):
  хранилище файлов, кэш, брокер, поиск, БД.
- Реализация по умолчанию — локальная (файловая система, Redis, RabbitMQ, Elasticsearch, PostgreSQL).
- **Точки подмены** задокументированы: S3/Azure Blob вместо ФС, Azure Service Bus вместо RabbitMQ,
  Azure Cache/ElastiCache вместо Redis, OpenSearch/Azure AI Search вместо Elasticsearch,
  Azure Database/Cloud SQL вместо локального PostgreSQL.
- Конфигурация — только через переменные окружения и `appsettings`, без плейнтекстных секретов в репозитории.
- **Никаких реальных вызовов облачных API, никаких аккаунтов, никаких внешних сетевых зависимостей**
  в обязательном пути запуска.

## 3. Жёсткие ограничения этого этапа

1. **Всё запускается на хосте через `docker compose`.** Никаких облачных деплоев, внешних сервисов и аккаунтов.
2. **Не трогать чужие Docker-ресурсы.** У пользователя есть другие образы и контейнеры — работать только
   в своём compose-проекте. Имена контейнеров/томов — с префиксом проекта. Не удалять чужие образы
   (`docker image prune` запрещён).
3. **Никаких секретов** в репозитории: только `.env`-пример и переменные окружения.
4. **Git-история сохраняется.** Не переписывать существующие коммиты, работать в `feature/*`, вливать в `main`
   через `--no-ff`. По завершении — тег `v2.0.0`.
5. **Прежний фронтенд удаляется**, но его тесты и артефакты прошлого этапа не удаляются из истории git.
6. **Развёртывание на хостинге/VDS** — вне зоны (нет аккаунтов). Документировать, но не делать.
7. Обязательный путь `docker compose up --build` не должен тянуть несуществующие или платные образы.
