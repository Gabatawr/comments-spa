## 0. Общие правила

- **Один origin.** SPA отдаётся nginx (`web`, хост-порт `8080`), который проксирует
  `/api/*` и `/ws` в контейнер `api` (внутренний порт `8080`). Прямой доступ к API —
  хост-порт `8081` (для отладки/QA).
- Формат: JSON UTF-8 (`application/json`), кроме загрузки (`multipart/form-data`) и бинарных
  вложений.
- Даты: ISO-8601 UTC с суффиксом `Z`, например `2026-10-04T22:30:00Z`. В PostgreSQL —
  `timestamptz`.
- Ошибки валидации: HTTP 400, тело v1-формата:
  ```json
  {
    "title": "Validation failed",
    "status": 400,
    "errors": {
      "userName": ["User Name may contain only latin letters and digits."],
      "captcha": ["CAPTCHA answer is invalid or expired."]
    }
  }
  ```
- Прочие ошибки: HTTP 4xx/5xx + `{ "title": "...", "status": N, "detail": "..." }`.
- Все тексты ошибок — на английском (их показывает UI).
- **Идентификация клиента.** Сервер сохраняет `clientIp` и `userAgent` каждого комментария
  (см. §1 и §6). Это обязательное требование ТЗ.

### 0.1. Идентификаторы

| Сущность | Тип в API | Тип в PostgreSQL |
|---|---|---|
| Comment.Id | `int` (JSON number) | `bigint GENERATED BY DEFAULT AS IDENTITY` |
| Attachment.Id | `int` | `bigint GENERATED BY DEFAULT AS IDENTITY` |

JSON-числа могут превышать 2^31; клиент Angular использует `number`. Для ключей > 2^53
(недостижимо на этом этапе) API не гарантирует точность. Keyset-курсор (§4) несёт id как строку.

## 1. DTO (JSON-контракт, без изменений по полям v1 + новые поля)

### CommentDto
```json
{
  "id": 12,
  "parentId": null,
  "userName": "Alice",
  "email": "alice@example.com",
  "homePage": "https://example.com",
  "text": "<strong>Hello</strong> &amp; <i>welcome</i>",
  "textPlain": "Hello & welcome",
  "createdAt": "2026-10-04T22:30:00Z",
  "clientIp": "203.0.113.7",
  "userAgent": "Mozilla/5.0 ...",
  "attachment": null,
  "replyCount": 2,
  "replies": []
}
```
- `text` — уже санитизированный сервером HTML (allow-list: `a[href,title]`, `code`, `i`, `strong`).
- `textPlain` — текст без тегов.
- `replies` — **полное дерево** потомков, отсортировано по `createdAt` ASC (`ThenBy Id` ASC).
- `homePage`, `clientIp`, `userAgent`, `attachment` могут быть `null`.
- `clientIp` — IPv4/IPv6 **первого доверенного хопа** (см. §6).
- `userAgent` — обрезан до 512 символов.

### AttachmentDto
```json
{
  "id": 7,
  "fileName": "photo.png",
  "contentType": "image/png",
  "kind": "image",
  "sizeBytes": 12345,
  "width": 320,
  "height": 240,
  "url": "/api/attachments/7",
  "thumbUrl": "/api/attachments/7/thumb"
}
```
- `kind`: `"image"` | `"text"`.
- Для `text`: `width`/`height`/`thumbUrl` = `null`.
- Для image `width`/`height` — размеры **после** пропорционального уменьшения (≤ 320×240,
  апскейл запрещён).

## 2. REST — сохранённые ручки v1

### 2.1 `GET /api/health`
Возвращает 200, даже если часть зависимостей в статусе `degraded` (compose healthcheck смотрит
на 200 + `status != "down"`). **[NEW]** поля `redis`, `broker`, `search`, `storage`:

```json
{
  "status": "ok",
  "database": "ok",
  "cache": "ok",
  "queue": { "pending": 0, "processed": 12 },
  "websocket": { "clients": 1 },
  "redis": "ok",
  "broker": "ok",
  "search": "ok",
  "storage": "ok",
  "version": "2.0.0"
}
```
- `status`: `"ok"` если `database == "ok"`, иначе `"degraded"`.
- Значения зависимостей: `"ok"` | `"error"` | `"disabled"` (фича выключена конфигом).
- `queue` — счётчики консьюмера (в broker-режиме: `pending` = неподтверждённые, `processed` = ack).
- **`GET /api/health/live`** — process liveness, всегда 200 `{"status":"ok"}` (для orchestration).
- **`GET /api/health/ready`** — 200 если БД доступна, иначе 503 (для оркестратора).

### 2.2 `GET /api/captcha`
```json
{ "captchaId": "6f1c…", "image": "data:image/png;base64,…", "expiresInSeconds": 300 }
```
- 6 символов: заглавные латинские + цифры, без `0/O/1/I`.
- Код клиенту не возвращается, one-time use, TTL 5 мин.
- **[NEW]** хранилище CAPTCHA — `ICaptchaStore` (по умолчанию Redis, fallback — память).

### 2.3 `GET /api/comments` — страница корневых комментариев
Query-параметры (v1 без изменений + **[NEW]** keyset):

| Параметр | Тип | По умолчанию | Допустимые значения |
|---|---|---|---|
| `page` | int | `1` | ≥ 1 (offset-режим) |
| `pageSize` | int | `25` | 1..100 |
| `sortBy` | enum | `createdAt` | `createdAt` \| `userName` \| `email` |
| `sortDir` | enum | `desc` | `asc` \| `desc` |
| `cursor` **[NEW]** | string | — | opaque keyset-курсор; если задан, `page` игнорируется |

Ответ 200 (v1 + **[NEW]** `nextCursor`):
```json
{
  "items": [ /* CommentDto[] */ ],
  "page": 1,
  "pageSize": 25,
  "totalItems": 42,
  "totalPages": 2,
  "sortBy": "createdAt",
  "sortDir": "desc",
  "nextCursor": "eyJ2IjoiMjAyNi0xMC0wNFQyMjozMDowMFoiLCJpZCI6MTJ9"
}
```
- Дефолт — **LIFO**: `sortBy=createdAt&sortDir=desc`.
- Сортировка только по корням; `replies` всегда ASC.
- `page` вне диапазона → пустой `items` (не 404).
- `totalItems`/`totalPages` считают **только корневые** комментарии.

### 2.4 `GET /api/comments/{id}`
Один комментарий (корень или ответ) с полным деревом. 404 если нет.

### 2.5 `POST /api/comments` — создание (multipart/form-data)
Поля формы — без изменений:

| Поле | Обяз. | Правила |
|---|---|---|
| `userName` | да | 3..50, `^[A-Za-z0-9]+$` |
| `email` | да | валидный email, ≤ 100 |
| `homePage` | нет | абсолютный `http(s)://` URL, ≤ 200; пусто = null |
| `text` | да | 1..5000; allow-list тегов; проверка закрытия (валидный XHTML) |
| `captchaId` | да | из `GET /api/captcha` |
| `captchaAnswer` | да | сравнение без учёта регистра |
| `parentId` | нет | id существующего комментария |
| `attachment` | нет | JPG/JPEG/PNG/GIF ≤ 5 МБ **или** TXT ≤ 100 КБ |

Ответ 201 + `Location: /api/comments/{id}`:
```json
{ "comment": { /* CommentDto */ } }
```
Ошибки: 400 + `errors` (ключи `userName`, `email`, `homePage`, `text`, `captcha`, `parentId`,
`attachment`).

**[NEW]** сервер обязан записать `clientIp`/`userAgent` из запроса (§6).

### 2.6 `POST /api/preview`
Request `application/json` `{ "text": "<b>hi</b>" }`, ответ 200 даже при невалидном тексте:
```json
{ "valid": false, "html": "<strong>hi</strong>", "plain": "hi", "errors": ["Tag <b> is not allowed."] }
```

### 2.7 `GET /api/attachments/{id}` и `GET /api/attachments/{id}/thumb`
`image/*` и `text/plain; charset=utf-8` — inline. Заголовки: `Content-Disposition: inline;

**[NEW]** файл читается через порт `IFileStorage` (FS по умолчанию, S3/Azure Blob — точка подмены).

### 2.8 `GET /api/dev/captcha/{captchaId}` — только Development
`{ "captchaId": "...", "code": "AB12CD" }`. Требует `ASPNETCORE_ENVIRONMENT=Development`
**и** `Features:DevCaptchaPeek=true`. В Production → 404.

### 2.9 `WS /ws`
При подключении:
```json
{ "type": "hello", "message": "connected", "clients": 2 }
```
При создании комментария (рассылается **всем инстансам API** через RabbitMQ, не только
локальным клиентам):
```json
{ "type": "comment.created", "eventId": "…uuid…", "comment": { /* CommentDto */ } }
```
`{"type":"ping"}` → `{"type":"pong"}`. Невалидный JSON игнорируется, соединение не рвётся.

## 4. Сортировка и пагинация — точные правила

1. **Значения по умолчанию:** `sortBy=createdAt`, `sortDir=desc` (LIFO), `pageSize=25` (жёсткий
   дефолт ТЗ), `page=1`.
2. **Регистронезависимая сортировка** `userName`/`email`: сервер сортирует по `lower(value)`
   (НЕ по SQLite-collation `NOCASE`; PostgreSQL-эквивалент — функциональный индекс
   `lower(user_name)`), затем `id ASC` как tie-breaker. Одинаковая семантика для SQL и GraphQL.
3. **Tie-breaker везде:** `id ASC` (детерминированный порядок).
4. **Offset-пагинация** (`page`) — контракт ТЗ; остаётся рабочей. `totalPages = ceil(total/pageSize)`,
   при `total == 0` → `0`.
5. **Keyset-пагинация** (`cursor`) — Middle+ путь для глубоких страниц без `OFFSET`:
   - курсор = `base64url(JSON { "s": sortBy, "d": sortDir, "v": "<value>", "id": <id> })`;
   - `v` — `createdAt` (ISO-8601 UTC) для `createdAt`, `lower(value)` для `userName`/`email`;
   - предикат: `(v, id) > (cursor.v, cursor.id)` для `asc`, `<` для `desc`;
   - несовпадение `sortBy/sortDir` с курсором → 400 `{"detail":"Cursor does not match sort."}`;
   - `nextCursor` есть тогда и только тогда, когда в БД есть ещё страница.
6. **Дерево ответов:** потомки любого узла сортируются `createdAt ASC, id ASC`, глубина не
   ограничена; сборка — level-by-level (BFS) одним запросом на уровень.
7. `pageSize > 100` → зажимается до 100. `pageSize < 1` → 25. `page < 1` → 1.
8. Неизвестные `sortBy`/`sortDir` → fallback на дефолт (не 400), как в v1.

## 5. GraphQL-схема (HotChocolate)

```graphql
enum CommentSortField { CREATED_AT USER_NAME EMAIL }
enum SortDirection { ASC DESC }

type Query {
  """Страница корневых комментариев с полным деревом ответов."""
  comments(
    page: Int = 1
    pageSize: Int = 25
    sortBy: CommentSortField = CREATED_AT
    sortDir: SortDirection = DESC
    cursor: String
  ): CommentPage!

  """Один комментарий (корень или ответ) с деревом."""
  comment(id: Long!): Comment

  """Поиск (Elasticsearch) с подсветкой."""
  search(query: String!, page: Int = 1, pageSize: Int = 25): SearchPage!
}

type Mutation {
  """Создание комментария/ответа. CAPTCHA обязательна."""
  createComment(input: CreateCommentInput!): CreateCommentPayload!
}

input CreateCommentInput {
  userName: String!
  email: String!
  homePage: String
  text: String!
  parentId: Long
  captchaId: String!
  captchaAnswer: String!
}

type CreateCommentPayload {
  comment: Comment
  errors: [ValidationError!]!
  """Истинно, если запись создана."""
  success: Boolean!
}

type ValidationError { field: String! message: String! }

type CommentPage {
  items: [Comment!]!
  page: Int!
  pageSize: Int!
  totalItems: Int!
  totalPages: Int!
  sortBy: CommentSortField!
  sortDir: SortDirection!
  nextCursor: String
}

type Comment {
  id: Long!
  parentId: Long
  userName: String!
  email: String!
  homePage: String
  text: String!
  textPlain: String!
  createdAt: DateTime!
  clientIp: String
  userAgent: String
  attachment: Attachment
  replyCount: Int!
  replies: [Comment!]!
}

type Attachment {
  id: Long!
  fileName: String!
  contentType: String!
  kind: String!
  sizeBytes: Long!
  width: Int
  height: Int
  url: String!
  thumbUrl: String
}

type SearchPage {
  items: [SearchHit!]!
  query: String!
  took: Int!
  page: Int!
  pageSize: Int!
  totalItems: Int!
  totalPages: Int!
}

type SearchHit {
  comment: Comment!
  score: Float!
  highlight: String
}
```

Правила:
- `comments` использует тот же read-сервис, что REST (`ICommentQueryService`); сортировка/пагинация
  идентичны §4.
- `createComment` вызывает тот же `ICommentCreateService` + валидацию + CAPTCHA, что REST;
  при ошибках `errors` непустой, `comment = null`, `success = false`, HTTP 200 (GraphQL-семантика).
- Ошибка CAPTCHA и прочие валидации — не GraphQL-ошибка транспорта, а часть payload.
- Лимит сложности запроса: 300; глубина: 15 (`AddMaxExecutionDepthRule`).

## 6. Клиентский IP и User-Agent — точные правила

1. В `Program.cs` включается `UseForwardedHeaders` с `ForwardedHeaders.XForwardedFor |
   XForwardedProto | XForwardedHost`.
2. `KnownNetworks`/`KnownProxies` очищаются **только** когда `Proxy:TrustAll=true` (по умолчанию
   в compose — `true`, потому что nginx стоит перед api в изолированной compose-сети). В
   Production-конфиге с известным диапазоном — указывается `Proxy:KnownProxies`.
3. Порядок определения `clientIp`:
   1. первый непустой элемент `X-Forwarded-For` слева (реальный клиент),
   2. `X-Real-IP`,
   3. `HttpContext.Connection.RemoteIpAddress`.
4. Обрезка до 64 символов; невалидное значение не отбрасывается (хранится как есть), но
   обязательно заносится в лог на Debug.
5. `userAgent` — заголовок `User-Agent`, обрезка до 512 символов, пусто → `null`.
6. Оба поля попадают в `CommentDto` и в событие `CommentCreated`.
7. **Проверка e2e (QA):** `curl -H 'X-Forwarded-For: 203.0.113.7, 10.0.0.1'` → в ответе
   `clientIp == "203.0.113.7"`.

## 7. События (RabbitMQ) — формат

### 7.1 Топология
- Exchange `comments.events` — `topic`, durable.
- Exchange `comments.dlx` — `topic`, durable (dead-letter).
- Очереди. **Важно (fan-out vs work-queue):** WebSocket-broadcast должен доходить до
  **каждого** инстанса API, поэтому для WS используется **пер-инстансная** очередь
  (auto-delete, exclusive, привязка к `comments.events` с ключом `comment.created`), а не
  общая durable-очередь: общая очередь даёт work-queue семантику (RabbitMQ раздаёт сообщение
  ровно одному консьюмеру), и тогда только один инстанс разошлёт событие своим клиентам.
  Индексация и инвалидация кэша — идемпотентные операции, им нужна именно work-queue
  семантика (одна обработка на кластер).

  | Очередь | Тип | Routing key | Назначение | DLQ |
  |---|---|---|---|---|
  | `comments.events.ws.<instanceId>` | auto-delete, exclusive, per-instance | `comment.created` | WebSocket broadcast **на каждом** инстансе | нет (live-сообщения не персистятся) |
  | `comments.events.search` | durable, shared | `comment.created` | индексация в Elasticsearch (ровно один раз) | `comments.events.search.dlq` |
  | `comments.events.cache` | durable, shared | `comment.created` | инвалидация кэша страниц (идемпотентно) | `comments.events.cache.dlq` |

  Для обратной совместимости и однoинстансного запуска допускается durable-очередь
  `comments.events.ws`; при `Messaging:ReplicaCount>1` (или всегда в Redis/ES-режиме) адаптер
  обязан использовать пер-инстансную очередь.
- Retry: `x-dead-letter-exchange=comments.dlx` + TTL-очередь `comments.events.retry` (5 s), после
  3 доставок — в `*.dlq`. Публикация — publisher confirms; HTTP-ответ **не ждёт** обработки.

### 7.2 Envelope
```json
{
  "eventId": "1e0c6f7a-8f2b-4a5e-9d3a-2b6c9f0f2a11",
  "eventType": "CommentCreated",
  "version": 1,
  "occurredAt": "2026-10-04T22:30:00.1234567Z",
  "producer": "comments-api",
  "payload": { "comment": { /* CommentDto */ } }
}
```
- `contentType: application/json`, `deliveryMode: 2` (persistent), `messageId = eventId`.
- Внутренняя шина (`IEventBus`) сохраняется как fallback-режим (`Messaging:Provider=inmemory`)
  — используется тестами без брокера и локальным запуском без RabbitMQ.

### 7.3 Доменные события
| `eventType` | Когда | Payload |
|---|---|---|
| `CommentCreated` | после commit вставки | `{ comment: CommentDto }` |
| `CommentIndexed` | после успешной индексации в ES | `{ commentId, indexedAt }` |
| `CommentSearchIndexFailed` | после N неудачных индексаций | `{ commentId, error }` |

| Ключ | TTL | Инвалидация |
|---|---|---|
| `comments:page:{sortBy}:{sortDir}:{page}:{pageSize}:v{N}` | 30 s | bump `comments:version` |
| `comments:version` | ∞ | `INCR` по событию `CommentCreated` |
| `comments:item:{id}` | 30 s | `DEL` по событию |
| `captcha:{captchaId}` | 300 s | one-time `GETDEL` при проверке |
| `stats:totals` | 60 s | bump по событию |

- Реализация за портом `ICacheService`; `Cache:Provider=redis|memory`.
- Generation-версия — в Redis, чтобы инвалидация работала между инстансами API.
- Если Redis недоступен — health `cache=error`, приложение продолжает работать на memory-fallback
  (graceful degradation, не 500).

## 12. Совместимость с v1 (для 251 теста)

- Все ручки §2 сохраняют URL, поля, коды и формат ошибок v1.
- `sortBy`/`sortDir` fallback, `page`/`pageSize` clamping, 400-shape — без изменений.
- Меняется только: провайдер БД (PostgreSQL), case-insensitive сортировка (lower() вместо
  SQLite `NOCASE`), хранилище CAPTCHA (порт с memory-fallback), способ доставки событий
  (broker с in-memory fallback). Ожидания тестов менять не нужно.
- Новые поля в `health` — аддитивны; тест `HealthTests` проверяет наличие старых ключей.
