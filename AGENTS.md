  XSS allow-list + проверка закрытия тегов, строгая валидация, CAPTCHA (PNG, TTL, one-time),

- **Frontend** `src/Frontend/` — SPA на ES-модулях без сборки. **Подлежит полной замене на Angular.**
- **Тесты** `tests/` — 251 xUnit, e2e-скрипт, DOM-харнесс. **Должны продолжать проходить.**
- **Инфраструктура** — `Dockerfile` (multi-stage, non-root, healthcheck), `docker-compose.yml`,
  `README.md`, `db/schema.sql` (MySQL-диалект) + `db/schema.md`, `scripts/`.

Проверено вживую: приложение работает, контейнер `healthy`, `/api/health` отвечает, 251/251 тест зелёный.

## Что нужно сделать

Пройди по `docs/target-middle-plus.md` целиком. Кратко:

1. **Clean Architecture** — разложить на проекты `Domain` / `Application` / `Infrastructure` / `Api`,
   зависимости строго внутрь, инфраструктура — за интерфейсами-портами.
2. **PostgreSQL** вместо SQLite (Npgsql, миграции, идемпотентный старт).
3. **Angular SPA** — полная замена прежнего фронта, сборка в Docker multi-stage.
4. **Middle**: Redis (кэш), RabbitMQ (очередь/брокер + доменные события), GraphQL, Elasticsearch (поиск).
5. **Middle+**: архитектура под 1M сообщений / 100k пользователей в сутки + **реально прогнанный нагрузочный
   тест k6** с отчётом и разбором узких мест.
6. **IP + User-Agent** клиента сохраняются и отдаются; корректная обработка `X-Forwarded-For` за прокси.
7. **Cloud-ready, но без облака**: швы под S3/Azure Blob, Service Bus, ElastiCache, OpenSearch — задокументированы,
   но реализация локальная. Никаких реальных облачных вызовов.

## Жёсткие ограничения

- **Всё поднимается одной командой `docker compose up --build` на хосте.** Никаких облачных деплоев и аккаунтов.
- **Не трогать чужие Docker-ресурсы.** В системе есть другие образы и контейнеры пользователя.
  Работать только в своём compose-проекте; имена контейнеров/томов — с префиксом проекта.
  **Запрещено**: `docker image prune`, `docker system prune`, удаление чужих образов и контейнеров.
- **Секретов в репозитории нет.** Только `.env.example` и переменные окружения.
- **Не переписывать существующую git-историю.** Работать в `feature/*`, вливать в `main` через `--no-ff`.
  По завершении — тег `v2.0.0`.
- **Не ломать существующее.** 251 тест либо продолжает проходить, либо осознанно адаптируется под PostgreSQL —
  с объяснением в отчёте. Скорее пустое, чем молча удалённое.
- **Развёртывание на хостинге/VDS** — вне зоны. Описать в README, но не делать.

## Процесс

1. **Сначала заморозь контракт.** Изучи существующий `docs/API.md`, составь `docs/API-v2.md`:
   REST-ручки, схема GraphQL, формат событий, модель данных с IP/User-Agent, правила сортировки/пагинации.
   Контракт фиксируется **до** распараллеливания работ — иначе фронт и бэк разъедутся.
2. **Разложи работу на доску задач** с зависимостями и `writeScopes`. Зоны должны быть разведены по каталогам.
3. **Подними ростер.** Ориентир — 4–6 участников: например `api` (backend и Clean Architecture),
   `web` (Angular), `infra` (PostgreSQL/Redis/RabbitMQ/Elasticsearch/compose), `perf` (нагрузка и k6),
   `qa` (тесты, чеклист, adversarial-проверка). Лид держит корень: контракт, `docs/*.md`, `README.md`,
   `db/**`, `scripts/**`, `docker-compose.yml`, слияния и приёмку.
4. **У каждого — своя зона записи.** Все работают в **одном** рабочем каталоге, блокировок нет.
   Пересечения по путям — главный источник конфликтов; разводите по каталогам и предупреждайте друг друга.
5. **Приёмка обязательна и проверяема.** Чистая сборка с нуля, тесты, `docker compose up --build`,
   прогон k6. В конце — отчёт в `docs/qa/` со списком того, что **не** сделано и почему. Пустая похвала
   бесполезна; честный список пробелов — ценен.
